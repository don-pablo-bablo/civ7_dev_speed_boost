# Contributing

## How it works

Each option is a dropdown in Advanced Setup. Each value after the first has a
criterion in the modinfo that matches it, and an action group that loads one
small file for it. Everything under `mod/` is generated from one table.

| path | what it is |
|---|---|
| `tools/build.py` | the `OPTIONS` table and the generator; the only file to edit |
| `mod/dev-speed-boost/` | the mod, all generated by `tools/build.py` |
| `.../config/options.xml` | the two Advanced Setup sections and their dropdowns |
| `.../text/en_us/DevSpeedBoostText.xml` | every name and tooltip |
| `.../data/modifiers-gameeffects.xml` | one modifier per option value |
| `.../data/options/` | one file per option value, loaded only when that value is chosen |
| `screenshots/` | in-game shots for the README |
| `workshop/description.txt` | the Steam Workshop page text, in Steam markup |

After editing `OPTIONS`, run `python3 tools/build.py` and commit what it
writes. Hand edits under `mod/` are overwritten.

## Code rules

- **Defaults**: every option's first value must change nothing. The mod is
  meant to stay installed.
- **Setup values**: never numeric. A value of `"5"` is stored as a number and
  the modinfo criterion never matches it. `config_value` turns each value into
  text such as `COSTS_5`.
- **Setup text**: always a LOC key. The game parses any other string as an ICU
  message, and a comma breaks it. `loc` writes the keys and refuses braces and
  apostrophes, which are ICU syntax.
- **Modifiers**: ids start `DSB_`. Boosts are human-only through
  `REQUIREMENT_PLAYER_IS_HUMAN`. Effects on cities, units or plots are
  attached through the player with `EFFECT_ATTACH_MODIFIERS`.
- **Effects**: before using one, find a shipped modifier with the same
  collection and owner, and copy its arguments. An effect can load without
  error and do nothing when its owner differs. `IgnoreAll=true` on
  `EFFECT_UNIT_ADJUST_IGNORE_MOVEMENT_OBSTACLE` did exactly that on player
  units.
- **Sections**: `group_of` puts an option in "every player" when it changes
  rules the AI shares, and in "human players" otherwise. Tooltips do not
  repeat what the section title says.
- **README**: keep its options tables, and the lists in
  `workshop/description.txt`, in step with `OPTIONS`.

## Testing

Options apply at game start, so every check is a new game. A change to the
setup sections or their text needs a full game restart as well.

- **Which options loaded**: `Modding.log` lists each action group applied at
  game start, such as `* dsb-costs-10`.
- **What the setup screen stored**: `GameCoreAppConfig.log`, keyed by hash.
- **Errors**: `Database.log` for data, `Localization.log` for text.

The data can also be checked offline, and a running game read directly, with a
development tool we use that has not been released publicly yet.

## Writing style

This applies to docs, comments, commit messages and the text players see in
the setup screen.

Plain English, blunt, short. If ten words will do, do not write a hundred. The
reader is busy and wants the important bits. The prose stays neutral
international English. Avoid buzzwords and jargon unless there is no other way
to say it.

- **Em-dashes**: do not use them. Use a colon, a semicolon or a separate
  sentence.
- **Contrasts**: do not over-use "X, not Y". Vary it with "rather than",
  "instead of" or a plain restatement.
- **Asides**: keep brackets rare. Move a secondary thought into its own
  sentence. Terse labels in reference tables are fine.
- **Headings**: sentence case. Write bulleted definitions as
  **term**: description.
- **Program output**: quote it verbatim, including punctuation and symbols.
- **Filler**: every sentence must add a fact, an example or a consequence.
  Do not write meta-framing such as "X is the default; Y is the exception".
  State the rule and give the case.
- **Names**: do not name individual people in the code, docs or commits.

Setup-screen text has two more rules:

- **Tooltips**: a value's tip appears under the option's description, so leave
  it empty unless it adds a fact its label does not give. Do not state an
  effect that has not been measured in game.
- **Characters**: no braces or apostrophes. `tools/build.py` refuses them.

## Commit messages

Plain English, imperative mood, no Conventional Commit prefixes. A subject line
is often the whole message. Add a body only when the reason is not obvious,
and keep it to a sentence or two. Do not write bulleted essays or restate the
diff.
